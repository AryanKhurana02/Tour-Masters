# Curated seed data

The current CSVs contain **synthetic demo fixtures** so the interface and complete homestay discovery flow can be exercised. Every record is labelled `DEMO FIXTURE - NOT VERIFIED`; the places, descriptions, scores, links, stays, and review dates are illustrative and are not travel guidance or real listings. The UI must keep a prominent end-of-page data note visible whenever these fixtures are loaded.

Before any real-user or production launch, replace the fixture rows with facts checked against verifiable sources, record a real reviewer and review date, and collect any required contact-publication consent. Never present fixture crowd estimates as observed counts, or fabricate real prices, availability, contact details, or travel times.

`python -m app.db.seed` creates `backend/pahadpath.db` and imports the CSV rows as an idempotent upsert by stable integer ID. All files are applied in one SQLite transaction; an invalid row or foreign key rolls the import back. Removed CSV rows are not deleted from the database: disable a record explicitly with `enabled=0` and retain its provenance.

Columns:

- `destinations.csv`: `id,name,district,region,description,tags,best_months,popularity_score,source_label,source_url,reviewer,reviewed_at,enabled`. Separate tags/month numbers with semicolons. Leave `popularity_score` empty when unknown.
- `alternative_links.csv`: `id,source_destination_id,alternative_destination_id,match_tags,travel_fit,source_label,source_url,reviewer,reviewed_at,enabled`. `travel_fit` is curated feasibility, not a duration or distance.
- `homestays.csv`: `id,destination_id,name,village,nightly_min,nightly_max,currency,public_contact,booking_url,publish_contact,amenities,source_label,source_url,reviewer,reviewed_at,enabled`. Prices are integer amounts in the stated three-letter currency. Do not put a contact or booking URL in this file unless explicit publication consent is recorded with `publish_contact=1`.
- `homestay_inventory.csv`: `id,homestay_id,inventory_date,total_units,available_units,inventory_mode,source_label,source_url,reviewer,reviewed_at,enabled`. This is **synthetic demo-only inventory**, not host-provided stock. `inventory_mode` must be `demo_mock`; unit counts and dates must never be presented as real availability. A submitted demo request is non-binding and does not reserve or decrement units.
- `local_events.csv`: `id,destination_id,region,name,starts_on,ends_on,pressure,source_label,source_url,reviewer,reviewed_at,enabled`.
- `event_calendar_reviews.csv`: `id,region,starts_on,ends_on,source_label,source_url,reviewer,reviewed_at,enabled`. A reviewed coverage row is required before absence of an event can be treated as zero pressure.

Dates must be ISO `YYYY-MM-DD`; score fields are integers from 0 to 100; booleans are `0` or `1`. Empty optional values stay unknown, not zero.

Workbook data in the `validation/` folder are user-supplied benchmark inputs, not independently verified facts. They are a qualitative offline benchmark only, not production inputs, live event data, or calibrated ground truth. The workbook is intended to compare model behavior against curated qualitative expectations, not to claim observed crowd counts or official holiday conditions. Only exact place-name matches count when evaluating crowd rankings; aliases or near matches are not treated as equivalent until the alias list is reviewed. The synthetic catalogue used here is intentionally limited: it is a small offline reference set, not a complete tourism dataset, and it should not be mistaken for a full historical or real-time source of crowd conditions.

To run the evaluator from the backend project root use:
`python -m scripts.evaluate_crowd`

The evaluator reports pairwise ordering, coverage, and concordance. Coverage is the fraction of benchmark pairs with a score available for both the crowded and quieter places. Concordance is the count of benchmark pairs where the model ranks the crowded place above the quieter place, after excluding ties. The output is diagnostic and qualitative: it measures how well the model matches the curated ordering, but it does not validate workbook values as factual truth or live observations. The synthetic catalogue remains a limited benchmark fixture and should not be used as production input, live crowd tracking, or a ground-truth dataset for operational decisions.

## Weather-backed crowd estimates

`weather_locations.csv` maps enabled catalogue destinations to separately reviewed OpenStreetMap place coordinates. Keep one location row per destination, preserve its source link, and verify the match before enabling it. Weather refresh uses Open-Meteo's daily archive for a five-year monthly climatology and its daily forecast (up to 16 days). Rain and temperature are converted to a rule-based weather visit-tendency input; this is not observed footfall, a live crowd count, or a calibrated crowd prediction.

From the `backend` directory, run `python -m scripts.refresh_weather` after seeding the catalogue and then every three hours (for example, with Windows Task Scheduler). The archive is refreshed every 30 days; forecast rows expire after three hours. Network access is only used by this refresh command. Recommendation and itinerary scoring read SQLite only, use a fresh forecast when available, fall back to the matching month's historical climatology, and otherwise use neutral 50 with a note. Raw daily CSVs and HTTP cache files are stored under `data/raw/weather/` and are ignored by Git. Check `GET /api/data-sources` for refresh status and retrieval timestamps. Weather must be described as an estimate and never as real-time crowd observations.

## Holiday crowd evaluation fixture

`validation/holiday_crowd_mapping.csv` is a normalized copy of a user-supplied holiday crowd workbook. Its destination groupings and dates have **not** been independently verified. The file is a qualitative, offline evaluation fixture only: it is not production input, verified event data, or calibrated ground truth. In particular, the listed crowded/quieter groupings must not be converted into numeric event pressures or used to alter production crowd scores.

From the `backend` directory, run `python -m scripts.evaluate_crowd` to compare the current SQLite-backed estimates with exact normalized destination names in the fixture. The JSON report includes pair coverage, concordant/tied/discordant pairs, missing names, and an `insufficient_coverage` status when fewer than five pairs can be scored. Name normalization handles case and spacing only; aliases such as a neighborhood and its parent destination are not matched until explicitly reviewed. The current catalogue may be synthetic, and low overlap is expected, so agreement is not evidence of real-world accuracy. The evaluator reads the existing database and does not refresh, seed, or mutate data or make network requests.

## Mussoorie case study and route context

Mussoorie is included as a real destination using the [Uttarakhand Tourism destination page](https://uttarakhandtourism.gov.in/destination/mussoorie). Its popularity score and best-month demand are intentionally blank because no verified numeric local source has been added. With missing inputs, the current backend scorer uses its documented neutral values (including neutral event pressure without reviewed calendar coverage and neutral weather) and labels the result estimated; a 50/100 result is a neutral placeholder, not a measured or validated crowd assessment. The qualitative holiday workbook is not used as a production event source.

The official [Uttarakhand Tourism homestays page](https://uttarakhandtourism.gov.in/homestays) did not expose source-verifiable Mussoorie listing records during review. Therefore no real homestay names, rates, contacts, or availability have been invented or added for Mussoorie. Existing catalogue stays remain clearly identified demo fixtures and are not real recommendations.

Recommendation scoring remains offline and SQLite-only. The Mussoorie case study may separately request a driving route from the Dehradun hub through the backend OpenRouteService integration. Configure `ORS_API_KEY` in `backend/.env` (never in frontend files) before enabling it. The supplied example host `https://openrouteservice.org` is not the directions endpoint; the integration uses `https://api.openrouteservice.org/v2/directions/driving-car`, an 8-second timeout, and only the route summary. The route is a town-centre estimate from approximate coordinates (Dehradun 30.3165, 78.0322; Mussoorie 30.4598, 78.0664), not door-to-door navigation. Verify these points before operational use. Route estimates do not report road closures, road safety, weather hazards, or accessibility and are not included in the crowd score. Review OpenRouteService's current usage limits and terms before enabling requests. Without a configured key the route endpoint returns an explicit not-configured response; all other discovery features continue to work.
